# Running simulations

## Overview
The initialization and simulation are performed separately. The main program only handles the simulation part. The generation of the mesh and the initial field is done by the scripts in the `scripts` directory. 
 The following types of input/output files are involved in a simulation:

- Configuration file

  The configuration file is in the [TOML](https://toml.io/en/) format. See example configuration files and the source files for parsing the configuration file for details.

- Grid file

    The grid file is named `grid.h5`, which is an HDF5 file containing the grid information, including `pex`, `pey`, `hbar`, `zz`, `zw`, `dz` and `dzw`. Currently, the main program only reads `zw` and calculates other coordinates from it. The domain size `pex`, `pey` and `hbar` are specified in the configuration file.

- Restart files

    Generally, the restart files have the file name format `restart{id}.h5`, where `{id}` is a 14-digit integer that indicates the simulation time (${id}={time}*10^8$). There may also be auxiliary data stored in `restart{id}_aux.h5`.

    When restart files are generated by the main program, symlinks `restart.h5` and `restart_aux.h5` are created to point to the latest restart files.

    One can either start simulations from `restart.h5` and `restart_aux.h5` or from specific restart ID. The restart file ID is specified by the option `--restart-from` when executing the main program.

- Output data

    The main program writes output data to files with the file name format `Sol{id}.h5`, where `{id}` is a 14-digit integer that indicates the simulation time (${id}={time}*10^8$).

- Monitoring data
    
    The main program writes statistics of the flow field into a subdirectory `monitor`.


## Command line options

The following command line options should be accepted by most programs:

| Option                      | Description                                                                         |
|-----------------------------|-------------------------------------------------------------------------------------|
| `-c`, `--config` *filename* | (optional) Specify the configuration file. (default: `param.toml`)                  |
| `--restart-from` *ID*       | (optional) Specify the restart file ID to start the simulation from.                |
| `--grid` *filename*         | (optional) Specify the grid file. (default: `grid.h5`, affects only the input grid) |
| `-h`, `--help`              | Print the help message.                                                             |


## Run an example
Copy the example case configuration where the main program is located. For example, the channel flow with $Re=180$ configuration:
```bash
cp /path/to/alps/examples/channel/param_channel180.toml .
```
Before executing the program, set the following environment variables to set the number of OpenMP threads per MPI process and the binding of the threads:
```bash
export OMP_NUM_THREADS=64
export OMP_PROC_BIND=close
export OMP_PLACES=cores
```
**The number of OpenMP threads should be adjusted** according to the CPU cores available and the number of MPI processes on each node. The variables `OMP_PROC_BIND` and `OMP_PLACES` bind the OpenMP threads to cores that are close to the main MPI process.

Run
```bash
mpiexec -n 4 ./{executable_name} --config=param_channel180.toml 
```
starts the simulation from the restart files. To start the simulation from a different restart file, add options `--restart-from`, which is followed by a restart file ID, e.g.
```bash
mpiexec -n 4 ./{executable_name} --config=param_channel180.toml --restart-from=5000
```

## Notes on MPI process and thread pinning
- It is recommended to use one GPU per MPI process.
- When running on CPUs, it is recommended to use one MPI process per NUMA node.
- The number of OpenMP threads set through `OMP_NUM_THREADS` should be equal to the number of cores available to each MPI process.
- MPI processes may need to bind to specific cores to achieve best performance. The OpenMP thread pinning should also be taken into consideration. Refer to MPI documentation for how to pin processes.
- Some modules or environment variables may need to be set to enable GPU-aware MPI. Otherwise, a segmentation fault can occur. Refer to MPI documentation for enabling GPU awareness.
